# Практическая работа: CI для Python-сервиса

## Цель

Настроить GitLab CI для Python-сервиса так, чтобы каждое изменение автоматически
проходило проверку качества кода, тесты, сборку Docker-образа и минимальную
проверку запуска сервиса.

Перед выполнением работы изучите [explained.md](explained.md). В нём находятся
объяснения основных понятий и справочные примеры, но нет готового pipeline для
этой работы.

## Сценарий

Команда разрабатывает небольшой HTTP-сервис. Локально сервис запускается, но
перед слиянием изменений в `main` необходимо автоматически проверить:

- качество Python-кода;
- корректность тестов;
- покрытие кода;
- возможность собрать Docker-образ;
- ответ запущенного контейнера на `/health`.

Основная часть работы относится только к CI. Автоматическое развёртывание на
сервер не требуется.

## Исходное состояние проекта

Создайте отдельный GitLab-репозиторий по шаблону:

`mlops-ci-<your_surname>`

Для работы можно использовать FastAPI-сервис из предыдущей практики. Перед
настройкой CI приведите репозиторий к следующей структуре:

```text
mlops-ci-<your_surname>/
  app/
    __init__.py
    main.py
  tests/
    test_health.py
  .dockerignore
  .gitignore
  Dockerfile
  README.md
  pyproject.toml
  poetry.lock
```

Требования к исходному проекту:

- используется Python 3.12;
- зависимости управляются Poetry;
- приложение импортируется как `app.main:app`;
- `GET /health` возвращает HTTP 200 и JSON `{"status": "ok"}`;
- `pytest`, `pytest-cov` и `httpx` находятся в группе `test`;
- `ruff` находится в группе `dev`;
- локальный тест проверяет код ответа и JSON `/health`;
- Dockerfile запускает сервис не от имени `root`;
- `.venv`, кэши, отчёты и локальные файлы окружения не добавлены в Git.

Перед первым CI-коммитом убедитесь, что локально проходят проверка Ruff, тесты и
сборка Docker-образа. Исправление исходного приложения не должно смешиваться с
отладкой `.gitlab-ci.yml`.

## Требования к runner

Для Python jobs подходит runner с Docker executor и образом Python 3.12.

Для Docker-сборки нужен runner, которому разрешена сборка контейнеров. До начала
работы выясните:

- какой executor использует доступный runner;
- требуется ли специальный runner tag;
- поддерживается ли Docker-in-Docker;
- включён ли privileged mode, если он необходим выбранному способу;
- какой способ сборки разрешён преподавателем или администратором.

Если Docker-сборка недоступна на обычном runner, используйте предоставленный
Docker runner или согласованный builder. Не отключайте защитные настройки
runner самостоятельно.

## Общие ограничения

- Основная ветка называется `main`.
- CI настраивается в корневом `.gitlab-ci.yml`.
- Версии базовых images и CI-инструментов должны быть зафиксированы.
- Не используйте теги images `latest`.
- Установка Python-зависимостей выполняется из `pyproject.toml` и
  `poetry.lock`.
- Обязательные проверки не должны использовать `allow_failure: true`.
- Секреты и пароли нельзя добавлять в Git или печатать в job log.
- Docker-образ должен соответствовать текущему `CI_COMMIT_SHA`.
- Pipeline должен работать после очистки cache.
- Не используйте ручной запуск команд на runner вместо описания job в CI.

## Часть 1. Базовая проверка CI

### 1. Первый pipeline

1. Создайте ветку `feature/ci` от актуальной `main`.
2. Добавьте `.gitlab-ci.yml` с одной диагностической job.
3. Job должна вывести версии Python и Poetry.
4. Отправьте ветку в GitLab и дождитесь завершения pipeline.
5. Сохраните ссылку на pipeline в отчёт.

Ожидаемый результат: pipeline создан автоматически, job назначена runner и
завершилась со статусом `passed`.

Если job остаётся в состоянии `pending`, не меняйте команды Python. Сначала
проверьте наличие runner и соответствие его tags.

### 2. Структура pipeline

Разделите pipeline минимум на три stages:

1. Проверки качества.
2. Тестирование.
3. Сборка.

Создайте отдельные jobs для Ruff, pytest и Docker. Имена jobs должны отражать
их назначение.

Проверка Ruff и тесты не используют результаты друг друга. Настройте pipeline
так, чтобы они могли начаться независимо, а Docker-сборка запускалась только
после успешного завершения обеих проверок.

Ожидаемый результат: на графе pipeline видны две независимые проверки и
зависящая от них Docker job.

## Часть 2. Воспроизводимое Python-окружение

### 3. Общая подготовка Python jobs

Для jobs Ruff и pytest настройте одинаковую базовую подготовку:

- образ Python 3.12 с зафиксированным полным тегом;
- зафиксированную версию Poetry;
- отключённый интерактивный ввод;
- установку зависимостей согласно `poetry.lock`;
- локальный для рабочей директории Poetry cache.

Не копируйте большой одинаковый блок команд в каждую job. Используйте один из
механизмов повторного использования YAML-конфигурации GitLab.

Ожидаемый результат: обе jobs используют одинаковую версию Python и Poetry, но
устанавливают только необходимые им группы зависимостей.

### 4. Cache зависимостей

Добавьте cache для загружаемых Poetry-пакетов.

Требования:

- cache находится внутри рабочей директории проекта;
- ключ зависит от `poetry.lock`;
- изменение lock-файла не должно использовать старый cache как единственный
  источник зависимостей;
- отсутствие cache не должно ломать pipeline;
- `.venv` не сохраняется как общий cache между jobs.

Запустите pipeline два раза для одного и того же коммита и сравните время
установки зависимостей. Очистите cache через интерфейс GitLab и повторите
pipeline.

Ожидаемый результат: после очистки cache pipeline остаётся успешным, а первый
повторный запуск обычно устанавливает зависимости быстрее.

## Часть 3. Качество и тестирование

### 5. Проверка Ruff

Job качества должна:

- запускать статическую проверку Ruff;
- проверять форматирование без автоматического изменения файлов;
- завершаться ошибкой при нарушении любого обязательного правила.

CI не должен автоматически исправлять код и создавать коммит. Исправления
выполняет разработчик, после чего отправляет новый коммит.

Ожидаемый результат: корректный код проходит job, а намеренно добавленное
нарушение приводит к статусу `failed`.

### 6. Тесты и покрытие

Job тестирования должна:

- запускать pytest;
- измерять покрытие пакета `app`;
- требовать покрытие не ниже 80 процентов;
- создавать JUnit XML;
- создавать Cobertura XML;
- сохранять HTML-отчёт покрытия;
- сохранять диагностические отчёты даже при падении тестов.

Укажите разумный срок хранения artifacts. Не сохраняйте `.venv` и весь checkout
как artifacts.

Ожидаемый результат:

- GitLab показывает результат тестов;
- отчёт покрытия доступен как artifact;
- недостаточное покрытие завершает job ошибкой;
- падение теста не уничтожает созданный JUnit-отчёт.

### 7. Проверка блокирующего поведения

Выполните два контролируемых эксперимента отдельными коммитами.

Первый эксперимент:

1. Добавьте очевидное нарушение Ruff.
2. Отправьте коммит.
3. Убедитесь, что pipeline завершился ошибкой и Docker job не началась.
4. Исправьте нарушение новым коммитом.

Второй эксперимент:

1. Временно измените ожидаемый результат теста `/health` на неправильный.
2. Отправьте коммит.
3. Убедитесь, что pytest job завершилась ошибкой и Docker job не началась.
4. Верните правильную проверку новым коммитом.

Не переписывайте историю после экспериментов. Не используйте
`allow_failure: true` и не отключайте проверки.

Ожидаемый результат: история репозитория показывает два обнаруженных CI вида
ошибок и последующие исправления.

## Часть 4. Сборка и smoke test

### 8. Docker build

Настройте Docker job с учётом возможностей доступного runner.

Job должна:

- запускаться только после успешных Ruff и pytest jobs;
- использовать совместимые зафиксированные версии Docker client и builder или
  service;
- собирать Dockerfile из текущего коммита;
- помечать образ полным или коротким идентификатором коммита;
- не использовать `latest` как единственный тег;
- выводить список созданных tags без вывода секретов.

Если применяется Docker-in-Docker, используйте безопасный вариант подключения,
поддерживаемый вашим runner. В отчёте объясните, зачем этому способу может быть
нужен privileged mode.

Ожидаемый результат: в логе видны успешная сборка и тег, однозначно связанный с
проверяемым коммитом.

### 9. Smoke test контейнера

В той же Docker job после сборки:

1. Запустите контейнер из только что собранного образа.
2. Дождитесь готовности сервиса с ограниченным числом попыток и общим
   тайм-аутом.
3. Проверьте HTTP-код и JSON `/health`.
4. При ошибке выведите логи контейнера.
5. Остановите и удалите тестовый контейнер независимо от результата проверки.

Не заменяйте ожидание готовности одной длительной фиксированной паузой.

Ожидаемый результат: job подтверждает не только сборку образа, но и минимальную
работоспособность запущенного приложения. После job на runner не остаётся
учебный контейнер.

## Часть 5. Условия запуска

### 10. Merge request pipeline

Настройте создание pipeline для:

- обычной ветки, пока для неё не открыт merge request;
- merge request;
- основной ветки;
- Git tag, начинающегося с `v`.

После открытия merge request для `feature/ci` не должно одновременно появляться
два одинаковых pipeline для одного коммита.

Проверьте отдельно:

1. Push в ветку до открытия merge request.
2. Push в ветку с открытым merge request.
3. Слияние в `main`.
4. Создание учебного тега вида `v0.1.0`.

В отчёте составьте таблицу: событие, создан ли pipeline, какие jobs появились и
почему.

Ожидаемый результат: правила дают предсказуемый набор pipeline и не создают
дубликаты для открытого merge request.

### 11. Проверка CI-конфигурации

Перед слиянием:

1. Проверьте `.gitlab-ci.yml` через CI Lint.
2. Посмотрите итоговую развёрнутую конфигурацию.
3. Убедитесь, что все jobs используют существующие stages.
4. Убедитесь, что Docker job зависит от реально существующих jobs.
5. Убедитесь, что pipeline запускается без локальных файлов, отсутствующих в
   Git.

Ожидаемый результат: CI Lint принимает конфигурацию, а последний pipeline
merge request полностью проходит.

## Дополнительное задание. Container Registry

Добавьте отдельную job публикации Docker-образа в GitLab Container Registry.

Требования:

- job появляется только для Git tags вида `v<major>.<minor>.<patch>`;
- образ получает тег Git tag и тег с идентификатором коммита;
- используются предопределённые registry variables или защищённые CI/CD
  variables;
- пароль не находится в `.gitlab-ci.yml` и не выводится в log;
- публикация зависит от успешных проверок и smoke test;
- повторный запуск для того же тега не создаёт образ из другого коммита.

Автоматически развёртывать опубликованный образ не требуется.

## Отчёт

Создайте файл `REPORT.md` и добавьте в него:

1. Ссылку на GitLab-репозиторий и merge request.
2. Версии Python, Poetry и Docker, использованные в CI.
3. Тип runner executor и способ Docker-сборки.
4. Схему stages и зависимостей между jobs.
5. Ссылку на последний успешный pipeline и его commit SHA.
6. Ссылки на два намеренно упавших pipeline из задания 7.
7. Причину каждого контролируемого падения и способ исправления.
8. Ссылку на JUnit-отчёт или его отображение в GitLab.
9. Ссылку на artifact с отчётом покрытия.
10. Результат запуска после очистки cache.
11. Таблицу поведения pipeline для branch, merge request, `main` и Git tag.
12. Объяснение различий между cache и artifacts на примере своей конфигурации.
13. Объяснение, почему успешная Docker-сборка без smoke test недостаточна.
14. Для дополнительного задания - адрес и tags опубликованного образа.

Не вставляйте в отчёт полные job logs. Приведите только необходимые фрагменты и
ссылки на GitLab.

## Критерии проверки

Работа считается выполненной, если:

- `.gitlab-ci.yml` проходит CI Lint;
- Ruff и pytest запускаются в отдельных jobs;
- Python-окружение создаётся из lock-файла;
- отсутствие cache не ломает pipeline;
- тестовая job публикует JUnit и coverage reports;
- порог покрытия действительно блокирует pipeline;
- Docker job не запускается после падения обязательной проверки;
- образ имеет тег, связанный с commit SHA;
- smoke test проверяет HTTP-код и JSON `/health`;
- временный контейнер очищается и после успешной, и после неуспешной проверки;
- правила не создают дублирующиеся pipeline для открытого merge request;
- секреты отсутствуют в репозитории и logs;
- отчёт содержит проверяемые ссылки и объясняет наблюдаемые результаты.
