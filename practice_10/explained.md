# Непрерывная интеграция и GitLab CI

Непрерывная интеграция, или CI, - это автоматическая проверка изменений проекта
после отправки коммита в удалённый репозиторий. CI помогает быстро обнаружить,
что новый код нарушил стиль, сломал тесты, перестал собираться или больше не
запускается в целевом окружении.

Этот файл является справочником. Он объясняет устройство CI и основные
возможности GitLab CI, но не содержит пошагового решения практической работы.

## Что проверяет CI

Типичный CI-процесс может включать:

- проверку формата и качества кода;
- модульные и интеграционные тесты;
- проверку типов;
- сборку Python-пакета или Docker-образа;
- проверку запуска собранного приложения;
- сохранение отчётов и других результатов проверки.

CI отвечает на вопрос: можно ли безопасно интегрировать изменение в основную
ветку. Автоматическое развёртывание приложения относится уже к CD. CI и CD
могут находиться в одном файле, но это разные этапы и разные уровни риска.

## Основные понятия

| Понятие | Назначение |
|---|---|
| Pipeline | Полный набор автоматических проверок для конкретного изменения |
| Job | Отдельная задача, например запуск тестов или сборка образа |
| Stage | Группа jobs, задающая крупный этап и порядок выполнения |
| Runner | Исполнитель, который получает job и запускает её команды |
| Executor | Способ запуска job: Docker, shell, Kubernetes и другие |
| Artifact | Файл, сохранённый как результат конкретной job |
| Cache | Повторно используемые файлы, ускоряющие следующие jobs |

Один pipeline обычно связан с конкретным коммитом. Поэтому в отчёте важно
сохранять не только общий статус, но и ссылку на pipeline и идентификатор
коммита, который был проверен.

## Файл .gitlab-ci.yml

GitLab читает конфигурацию из файла `.gitlab-ci.yml` в корне репозитория.
Конфигурация записывается в YAML, поэтому отступы являются частью синтаксиса.

Минимальный пример:

```yaml
stages:
  - verify

show_environment:
  stage: verify
  image: python:3.12-slim
  script:
    - python --version
```

Здесь определена одна stage и одна job. Job запускается в контейнере с Python и
печатает версию интерпретатора.

Имя job выбирает автор конфигурации. Ключи `stage`, `image` и `script` имеют
специальное значение для GitLab.

## Как устроен .gitlab-ci.yml

В конфигурации есть два основных уровня:

1. Глобальные секции описывают pipeline целиком и значения по умолчанию.
2. Секции jobs описывают отдельные задачи.

GitLab отличает их по имени верхнего уровня. Например, `stages`, `workflow`,
`variables`, `default` и `include` являются специальными глобальными ключами, а
`lint_python` или `build_docs` могут быть именами jobs.

```yaml
stages:
  - check

variables:
  APP_MODE: "ci"

check_source:
  stage: check
  script:
    - echo "$APP_MODE"
```

В этом примере `stages` и `variables` относятся ко всему pipeline, а
`check_source` является job.

### Основы YAML

При написании `.gitlab-ci.yml` важно соблюдать правила YAML:

- вложенность задаётся пробелами, а не табуляцией;
- элементы списка начинаются с `-`;
- после имени ключа ставится `:`;
- строки со специальными символами лучше заключать в кавычки;
- комментарий начинается с `#`;
- одинаковый ключ нельзя бездумно повторять на одном уровне;
- команды `script` обычно записываются списком строк.

Список:

```yaml
stages:
  - check
  - build
```

Вложенный словарь:

```yaml
artifacts:
  when: always
  paths:
    - reports/
```

Многострочная команда:

```yaml
script:
  - |
    if [ -f pyproject.toml ]; then
      echo "project file exists"
    else
      exit 1
    fi
```

YAML parser проверяет только структуру YAML. Он не знает, существуют ли
указанные stages, jobs, images и GitLab keywords. Семантику файла дополнительно
проверяет CI Lint.

## Глобальные секции

### workflow

`workflow` определяет, будет ли создан pipeline целиком. Чаще всего внутри
используют `workflow: rules`.

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

Если ни одно правило не совпало, pipeline не создаётся. Условия нужно проверять
для branch, merge request, tag и других используемых типов pipeline.

### stages

`stages` задаёт крупные этапы и их порядок:

```yaml
stages:
  - check
  - test
  - build
```

Каждая job ссылается на одно из этих имён через `stage`. Если `stage` не
указана, GitLab использует stage `test`, если она доступна в конфигурации.

### variables

Глобальный `variables` задаёт несекретные значения, доступные jobs:

```yaml
variables:
  APP_MODE: "ci"
  REPORT_DIR: "reports"
```

Job может переопределить значение внутри собственного `variables`. Секретные
значения в этот раздел не записывают.

### default

`default` хранит настройки, которые должны наследовать jobs:

```yaml
default:
  image: python:3.12.12-slim
  interruptible: true
  before_script:
    - python --version
```

Job может заменить поддерживаемое значение `default` собственной настройкой.
`default` не объединяет произвольные вложенные словари по частям, поэтому после
переопределения нужно проверять итоговую конфигурацию.

### include

`include` подключает другую CI-конфигурацию:

```yaml
include:
  - local: .gitlab/ci/common.yml
```

Файл можно подключать из текущего репозитория, другого проекта, шаблона или по
удалённому адресу. Для учебного pipeline одного файла обычно достаточно.
Разделение полезно, когда конфигурация стала большой или общий проверенный
шаблон используется несколькими проектами.

## Основные ключи job

| Ключ | Назначение |
|---|---|
| `stage` | Указывает этап job |
| `image` | Выбирает основной container image |
| `services` | Запускает дополнительные service containers |
| `tags` | Выбирает runners с подходящими tags |
| `variables` | Задаёт переменные только для этой job |
| `before_script` | Выполняет подготовительные команды |
| `script` | Выполняет основную проверку или сборку |
| `after_script` | Выполняет диагностику или очистку после `script` |
| `rules` | Определяет наличие и режим запуска job |
| `needs` | Задаёт точные зависимости от других jobs |
| `cache` | Настраивает повторно используемый cache |
| `artifacts` | Сохраняет файлы и структурированные отчёты |
| `allow_failure` | Разрешает pipeline продолжить работу после ошибки job |
| `when` | Задаёт момент или ручной режим запуска |
| `timeout` | Ограничивает максимальную длительность job |
| `retry` | Разрешает повтор для выбранных инфраструктурных ошибок |
| `interruptible` | Разрешает отменить устаревшую job новым pipeline |
| `environment` | Описывает среду развёртывания, а не окружение Python |

Job должна содержать `script` или другой ключ, который выполняет работу,
например `trigger`. Для обычной проверки используется `script`.

### stage

```yaml
check_names:
  stage: check
  script:
    - echo "check names"
```

Имя stage должно присутствовать в `stages`. Jobs одной stage могут выполняться
параллельно.

### image и services

`image` является средой выполнения job. `services` добавляет связанные
контейнеры, например базу данных:

```yaml
integration_check:
  image: python:3.12.12-slim
  services:
    - name: postgres:17.6-alpine
      alias: database
  script:
    - python scripts/check_database.py
```

Service не заменяет основной image. Job обращается к service по сетевому alias,
а не через `localhost`, если документация executor не говорит обратное.

### before_script, script и after_script

```yaml
example_job:
  before_script:
    - echo "prepare"
  script:
    - echo "main operation"
  after_script:
    - echo "collect diagnostics or clean resources"
```

- `before_script` подготавливает окружение;
- `script` определяет основной результат job;
- `after_script` запускается после основного блока и подходит для диагностики и
  очистки.

`after_script` выполняется в отдельном shell-контексте. Переменная, созданная
командой `export` внутри `script`, может быть там недоступна. Для очистки лучше
использовать заранее известные имена или CI/CD variables.

### rules

Каждый элемент `rules` проверяется сверху вниз. Первое совпавшее правило
определяет поведение job.

```yaml
tag_information:
  rules:
    - if: '$CI_COMMIT_TAG'
    - when: never
  script:
    - echo "$CI_COMMIT_TAG"
```

Внутри правила часто используются:

- `if` - условие по CI/CD variables;
- `changes` - изменение заданных файлов;
- `exists` - наличие файлов;
- `when` - режим запуска;
- `allow_failure` - допустимость ошибки для этого правила.

Основные значения `when`:

- `on_success` - обычный автоматический запуск;
- `always` - запуск независимо от результата предыдущих jobs;
- `manual` - ручной запуск пользователем;
- `never` - исключение job;
- `on_failure` - запуск после ошибки предыдущего этапа.

Старые ключи `only` и `except` встречаются в существующих проектах, но для
новой конфигурации лучше последовательно использовать `rules`.

### needs

```yaml
assemble:
  stage: build
  needs:
    - syntax_check
    - unit_check
  script:
    - echo "assemble"
```

`needs` указывает, какие jobs должны успешно завершиться. Job сможет начаться,
не дожидаясь несвязанных jobs предыдущих stages.

Если нужная job создаётся не во всех pipeline из-за `rules`, зависимость также
должна учитывать её отсутствие. Иначе GitLab может отклонить конфигурацию ещё
до запуска.

### cache

```yaml
cache:
  key:
    files:
      - poetry.lock
  paths:
    - .cache/pypoetry/
```

`key` определяет совместимость cache, а `paths` перечисляет сохраняемые пути.
Пути задаются относительно рабочей директории проекта.

Дополнительно можно управлять политикой:

- `pull-push` - скачать существующий cache и сохранить обновлённый;
- `pull` - только скачать;
- `push` - только сохранить.

### artifacts

```yaml
artifacts:
  when: always
  expire_in: 7 days
  paths:
    - reports/
```

Важные вложенные ключи:

- `paths` - обычные сохраняемые файлы;
- `reports` - отчёты известного GitLab формата;
- `when` - условие сохранения;
- `expire_in` - срок хранения;
- `name` - имя архива.

Artifacts относятся к конкретной job и pipeline. Они не являются постоянным
хранилищем релизов.

### allow_failure, retry и timeout

`allow_failure: true` подходит только для действительно необязательной
проверки. Ошибка такой job не блокирует успешный статус pipeline.

`retry` следует применять к ограниченному набору временных инфраструктурных
сбоев. Повтор не исправляет детерминированно падающий тест.

`timeout` ограничивает зависшую job. Значение должно учитывать нормальную
продолжительность операции, но не скрывать бесконечное ожидание.

## Скрытые jobs и extends

Имя, начинающееся с точки, создаёт скрытую job-шаблон. Она не запускается сама:

```yaml
.python_template:
  image: python:3.12.12-slim
  before_script:
    - python --version

check_one:
  extends: .python_template
  script:
    - echo "first check"

check_two:
  extends: .python_template
  script:
    - echo "second check"
```

`extends` уменьшает копирование одинаковых настроек. После наследования нужно
открыть итоговую конфигурацию в CI Lint и проверить, какие значения были
объединены, а какие заменены.

YAML anchors также умеют повторно использовать фрагменты, но `extends` обычно
понятнее для наследования GitLab jobs.

## Нейтральный каркас CI-файла

Ниже показано расположение основных секций. Это не готовый pipeline для
практической работы: команды и правила нужно выбирать по требованиям проекта.

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

stages:
  - check
  - package

variables:
  TOOL_MODE: "ci"

default:
  image: python:3.12.12-slim
  interruptible: true

.common_check:
  stage: check
  before_script:
    - python --version

first_check:
  extends: .common_check
  script:
    - echo "run first project check"

second_check:
  extends: .common_check
  script:
    - echo "run second project check"

create_result:
  stage: package
  needs:
    - first_check
    - second_check
  script:
    - mkdir -p output
    - echo "result" > output/result.txt
  artifacts:
    expire_in: 1 day
    paths:
      - output/
```

Порядок секций внутри файла выбирается для читаемости. Обычно сначала размещают
`workflow`, `stages`, глобальные `variables` и `default`, затем шаблоны и jobs в
порядке выполнения.

## Порядок stages и jobs

Stages выполняются в указанном порядке. Следующая stage обычно начинается
только после успешного завершения предыдущей.

Jobs внутри одной stage независимы и могут выполняться параллельно, если
доступны runners. Например, проверка стиля и тесты могут запускаться
одновременно, если ни одна из них не использует результат другой.

Если обязательная job завершается с ненулевым кодом возврата, pipeline получает
статус `failed`, а jobs следующих stages обычно не запускаются.

Не следует добавлять `allow_failure: true` к обязательной проверке только ради
зелёного pipeline. Такая настройка означает, что её ошибка сознательно не
блокирует интеграцию.

## Изоляция jobs

Каждая job запускается в новом окружении. Файлы, созданные в одной job, не
появляются автоматически в другой.

Из этого следуют важные правила:

- установка пакета в первой job не устанавливает его во второй;
- запущенный процесс не продолжает работать в следующей job;
- локальный Docker-образ одной job не доступен другой без передачи или
  публикации;
- необходимые результаты передаются через artifacts или внешнее хранилище.

Такая изоляция делает проверки воспроизводимыми и не позволяет случайному
состоянию предыдущей job скрыть проблему.

## Runner и image

Runner получает описание job и выполняет её. Доступные команды зависят от
executor и выбранного образа.

В Docker executor ключ `image` задаёт контейнер, внутри которого выполняется
`script`:

```yaml
inspect_python:
  image: python:3.12-slim
  script:
    - python --version
    - python -m pip --version
```

Наличие Docker на машине runner не означает, что команда `docker` автоматически
доступна внутри любой job. Для сборки образов runner и job должны быть
настроены соответствующим образом.

Теги runner позволяют направлять job только исполнителям с нужными
возможностями:

```yaml
build_on_docker_runner:
  tags:
    - docker
  script:
    - docker version
```

Конкретное имя тега зависит от настройки GitLab instance и runner.

## Подготовка окружения Python

CI должен устанавливать зависимости из файлов проекта, а не полагаться на
пакеты, случайно присутствующие в образе runner.

При использовании Poetry важны:

- поддерживаемая версия Python;
- зафиксированная версия Poetry;
- согласованные `pyproject.toml` и `poetry.lock`;
- установка только необходимых для job групп;
- запуск инструментов внутри окружения Poetry.

Пример общего шаблона job:

```yaml
python_check:
  image: python:3.12-slim
  before_script:
    - python -m pip install "poetry==<poetry_version>"
    - poetry install --no-interaction
  script:
    - poetry run python --version
```

`before_script` выполняется перед основным `script`. Версию Poetry следует
выбрать и зафиксировать осознанно. Запись без версии делает pipeline зависимым
от будущих изменений инструмента.

## Cache и artifacts

Cache и artifacts решают разные задачи.

| Механизм | Для чего используется |
|---|---|
| Cache | Ускоряет повторную загрузку зависимостей и других восстанавливаемых файлов |
| Artifact | Сохраняет результат job для человека или следующей job |

Кэш не является гарантированным хранилищем. Pipeline должен оставаться
работоспособным после очистки кэша.

Хорошим ключом кэша зависимостей является lock-файл. При его изменении должен
создаваться новый кэш:

```yaml
cache:
  key:
    files:
      - poetry.lock
  paths:
    - .cache/pypoetry/
```

Чтобы путь находился внутри рабочей директории проекта, можно заранее задать
переменную `POETRY_CACHE_DIR`.

Пример обычного artifact:

```yaml
artifacts:
  when: always
  expire_in: 7 days
  paths:
    - reports/
```

`when: always` полезен для диагностических отчётов: они сохраняются и при
неуспешной проверке.

Не следует кэшировать `.venv` без понимания executor, путей и совместимости.
Повторное использование окружения между разными образами Python может скрыть
ошибку или привести к несовместимости бинарных пакетов.

## Отчёты тестов и покрытия

Обычный текст в job log позволяет прочитать результат, но структурированные
отчёты GitLab может показать непосредственно в интерфейсе merge request.

Для Python обычно создают:

- JUnit XML с результатами тестов;
- Cobertura XML с покрытием кода;
- HTML-отчёт покрытия как обычный artifact.

Пример объявления уже созданных файлов:

```yaml
artifacts:
  when: always
  reports:
    junit: reports/junit.xml
    coverage_report:
      coverage_format: cobertura
      path: reports/coverage.xml
  paths:
    - reports/
```

Раздел `artifacts` не создаёт отчёты сам. Сначала тестовый инструмент должен
записать файлы по указанным путям.

Порог покрытия не заменяет проверку смысла тестов. Он лишь задаёт минимальную
долю выполненных строк или ветвей кода.

## rules и workflow

`rules` определяет, должна ли конкретная job присутствовать в pipeline.
Условия могут зависеть от:

- типа pipeline;
- ветки;
- тега;
- изменённых файлов;
- значения CI/CD variable.

Пример job только для основной ветки:

```yaml
main_branch_job:
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
  script:
    - echo "default branch"
```

`workflow: rules` управляет созданием pipeline целиком. Он особенно полезен для
разделения branch pipelines и merge request pipelines.

Неосторожные правила могут создать два pipeline для одного изменения: branch
pipeline и merge request pipeline. При проектировании условий нужно проверить
поведение как до, так и после открытия merge request.

## Предопределённые переменные

GitLab предоставляет контекст pipeline через предопределённые переменные.
Часто используются:

- `CI_COMMIT_SHA` - полный идентификатор коммита;
- `CI_COMMIT_SHORT_SHA` - сокращённый идентификатор;
- `CI_COMMIT_BRANCH` - имя ветки, если pipeline запущен для ветки;
- `CI_COMMIT_TAG` - имя тега, если pipeline запущен для тега;
- `CI_DEFAULT_BRANCH` - основная ветка проекта;
- `CI_PIPELINE_SOURCE` - причина создания pipeline;
- `CI_REGISTRY_IMAGE` - адрес образа проекта в GitLab Container Registry.

Не все переменные существуют во всех типах pipeline. Например, tag pipeline не
обязан иметь значение `CI_COMMIT_BRANCH`.

## Пользовательские переменные и секреты

Несекретные настройки можно объявлять в `.gitlab-ci.yml`:

```yaml
variables:
  APP_ENV: "ci"
```

Пароли, токены и приватные ключи нельзя сохранять в репозитории. Их добавляют в
настройках GitLab CI/CD Variables или получают из отдельного хранилища
секретов.

Для чувствительных переменных применяют подходящие свойства:

- masked скрывает значение в типичном выводе лога;
- hidden не позволяет повторно посмотреть значение в интерфейсе;
- protected ограничивает использование защищёнными ветками и тегами;
- file type передаёт секрет как путь к временному файлу.

Маскирование не защищает от намеренно вредоносного скрипта. Перед запуском
pipeline для недоверенного изменения нужно просматривать CI-конфигурацию.
Команды `env`, `printenv` и отладочная печать конфигурации могут раскрыть
чувствительные значения.

## needs и зависимости между jobs

По умолчанию порядок определяется stages. Ключ `needs` задаёт более точную
зависимость и позволяет job начать работу сразу после завершения необходимых
jobs.

```yaml
package:
  stage: build
  needs:
    - lint
    - unit_tests
  script:
    - echo "build package"
```

В этом примере `package` зависит от двух конкретных проверок. Pipeline образует
направленный граф без циклов.

`needs` не передаёт произвольные файлы автоматически. Если следующей job нужны
созданные файлы, их дополнительно объявляют artifacts и разрешают загрузку
этих artifacts.

## Сборка Docker-образа в CI

Способ сборки зависит от настройки runner. Возможные варианты:

- shell executor с доступом к локальному Docker daemon;
- Docker-in-Docker;
- подключение Docker socket;
- BuildKit, Buildah или другой специализированный builder.

Docker-in-Docker обычно требует privileged runner. Это дополнительный риск,
поэтому такой режим должен быть осознанно разрешён администратором. Нельзя
предполагать, что любой runner поддерживает Docker-сборку.

Если используются Docker CLI и Docker-in-Docker, их версии фиксируют и делают
совместимыми. Тег `latest` не подходит для воспроизводимого pipeline.

Образ полезно помечать неизменяемым идентификатором коммита. Один только тег
`latest` не позволяет точно установить, какой код находится внутри образа.

Перед публикацией в registry выполняют аутентификацию через CI/CD variables или
предопределённые учётные данные GitLab. Пароль не записывают в YAML и не
передают как открытый аргумент, который попадёт в log или историю shell.

## Smoke test

Smoke test проверяет минимальную работоспособность собранного приложения. Для
HTTP-сервиса обычно достаточно:

1. Запустить контейнер из только что собранного образа.
2. Дождаться готовности сервиса с ограниченным числом повторов.
3. Проверить код HTTP-ответа и минимальный контракт `/health`.
4. Остановить и удалить контейнер независимо от результата проверки.

Фиксированная длительная пауза менее надёжна, чем несколько коротких проверок с
общим тайм-аутом. Быстрый сервис не должен ждать лишнее время, а медленный не
должен случайно проверяться слишком рано.

Очистку временных контейнеров можно разместить в `after_script`, но следует
учитывать, что `after_script` выполняется в отдельном shell-контексте. Нужные
имена и пути должны быть доступны без локальных переменных предыдущего shell.

## Теги Docker-образов

Полезно различать:

- тег с идентификатором коммита для точной воспроизводимости;
- тег ветки для временной разработки;
- версионный Git tag для выпуска;
- `latest` как удобный указатель, но не как единственный идентификатор.

Имя Git-ветки может содержать `/` и другие символы, недопустимые в Docker tag.
Для веток используют заранее нормализованное значение, например slug,
предоставляемый CI-системой.

## Проверка конфигурации

До запуска pipeline полезно проверить:

1. Корректность YAML.
2. Корректность ключей GitLab CI.
3. Итоговую конфигурацию после `include`, шаблонов и наследования.
4. Наличие runner с нужными тегами и executor.
5. Локальную работоспособность команд из `script` в аналогичном контейнере.

Обычный YAML parser не знает семантику GitLab CI. Для окончательной проверки
используют CI Lint в GitLab.

## Диагностика ошибки

При падении pipeline нужно сначала определить слой проблемы:

- pipeline не создан - проверить `workflow: rules`;
- pipeline не проходит валидацию - проверить YAML и ключи GitLab CI;
- job ожидает runner - проверить доступные runners и их теги;
- подготовка image или service завершилась ошибкой - проверить registry и
  runner;
- установка зависимостей упала - проверить Python, Poetry и lock-файл;
- команда завершилась с ошибкой - воспроизвести точную команду локально;
- artifact не найден - проверить путь относительно корня job;
- Docker недоступен - проверить executor и способ подключения daemon.

Важно разделять эти уровни. Например, успешная YAML-валидация не доказывает,
что тесты прошли, а успешная сборка образа не доказывает, что сервис отвечает.

## Признаки хорошего CI

Хороший pipeline:

- воспроизводим из файлов репозитория;
- быстро сообщает о простых ошибках;
- не скрывает падения обязательных проверок;
- не зависит от файлов на компьютере разработчика;
- сохраняет полезные отчёты;
- не раскрывает секреты;
- собирает тот же коммит, для которого показан статус;
- очищает временные ресурсы;
- содержит только те jobs, которые действительно нужны для типа изменения;
- остаётся работоспособным после очистки кэша.
