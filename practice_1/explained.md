# Шпаргалка по Git

Git хранит историю изменений проекта. С его помощью можно фиксировать версии
файлов, работать в отдельных ветках, объединять изменения и возвращаться к
предыдущим состояниям.

Эта шпаргалка описывает основные команды и не содержит решения практической
работы.

## Основные области Git

При работе с Git важно различать четыре области.

| Область | Что в ней находится |
|---|---|
| Рабочая папка | Текущее содержимое файлов проекта |
| Индекс | Изменения, выбранные для следующего коммита |
| Локальный репозиторий | Коммиты и ветки на компьютере |
| Удалённый репозиторий | Общая копия репозитория на GitHub, GitLab или другом сервере |

Команда `git add` добавляет изменения в индекс. Команда `git commit` сохраняет
содержимое индекса в локальной истории. Команда `git push` отправляет локальные
коммиты в удалённый репозиторий.

## Первоначальная настройка

Настройка имени и электронной почты автора коммитов:

```bash
git config --global user.name "Student Name"
git config --global user.email "student@example.com"
```

Просмотр текущих настроек:

```bash
git config --list
```

Параметр `--global` применяет настройку ко всем репозиториям пользователя. Без
него настройка действует только в текущем репозитории.

## Создание локального репозитория

Создание нового репозитория в текущей папке:

```bash
git init
```

Клонирование существующего удалённого репозитория:

```bash
git clone <repository_url>
```

`git init` используется для нового локального проекта. `git clone` загружает
существующий проект вместе с его историей и настройкой удалённого репозитория.

## Проверка состояния

```bash
git status
```

Команда показывает:

- текущую ветку;
- изменённые файлы;
- новые неотслеживаемые файлы;
- изменения, уже добавленные в индекс;
- наличие незавершённого слияния или другой операции.

`git status` полезно выполнять до и после любой операции, изменяющей историю.

Краткий формат вывода:

```bash
git status --short
```

## Просмотр изменений

Изменения в рабочей папке, которые ещё не добавлены в индекс:

```bash
git diff
```

Изменения, добавленные в индекс:

```bash
git diff --staged
```

Изменения конкретного файла:

```bash
git diff -- path/to/file.py
```

Сравнение двух коммитов или веток:

```bash
git diff <first_revision> <second_revision>
```

## Добавление изменений в индекс

Добавление конкретного файла:

```bash
git add path/to/file.py
```

Добавление нескольких файлов:

```bash
git add file1.py file2.py
```

Интерактивный выбор отдельных частей файла:

```bash
git add -p
```

`git add -p` полезен, если в одном файле сделано несколько логически разных
изменений, которые нужно сохранить отдельными коммитами.

Удаление файла из индекса без удаления из рабочей папки:

```bash
git restore --staged path/to/file.py
```

## Создание коммитов

Коммит - это сохранённый снимок состояния проекта в определённый момент
времени. У каждого коммита есть уникальный идентификатор, автор, дата, сообщение
и ссылка на предыдущий коммит. Последовательность связанных коммитов образует
историю проекта.

В коммит попадают не все изменения рабочей папки, а только изменения, заранее
добавленные в индекс командой `git add`. Обычно один коммит соответствует одной
законченной задаче или одному логическому изменению.

```bash
git commit -m "Describe the change"
```

Хороший коммит содержит одно законченное логическое изменение. Сообщение должно
кратко отвечать на вопрос, что изменено.

Добавление новых изменений в последний локальный коммит:

```bash
git add path/to/file.py
git commit --amend
```

Изменение только сообщения последнего коммита:

```bash
git commit --amend -m "New commit message"
```

`--amend` заменяет последний коммит новым. Его не следует без необходимости
применять к коммиту, который уже используется другими участниками.

## Просмотр истории

Полная история текущей ветки:

```bash
git log
```

Краткая история всех веток в виде графа:

```bash
git log --graph --oneline --all --decorate
```

История конкретного файла:

```bash
git log -- path/to/file.py
```

Просмотр содержимого коммита:

```bash
git show <commit_hash>
```

Поиск коммитов по части сообщения:

```bash
git log --grep="search text"
```

## Ветки

Ветка - это отдельная линия разработки и одновременно имя, указывающее на
последний коммит этой линии. Новая ветка создаётся от выбранного коммита и
позволяет изменять проект независимо от других веток.

Например, основная версия проекта может находиться в ветке `main`, а разработка
новой функции выполняться в отдельной ветке. Коммиты новой функции не изменяют
`main`, пока ветки не будут объединены.

При создании нового коммита указатель текущей ветки автоматически начинает
указывать на этот коммит. Переключение ветки меняет файлы рабочей папки в
соответствии с состоянием выбранной линии разработки.

Просмотр локальных веток:

```bash
git branch
```

Просмотр локальных и удалённых веток:

```bash
git branch --all
```

Создание новой ветки:

```bash
git branch <branch_name>
```

Переход в существующую ветку:

```bash
git switch <branch_name>
```

Создание ветки и немедленный переход в неё:

```bash
git switch -c <branch_name>
```

Создание ветки от выбранной точки истории:

```bash
git switch -c <branch_name> <start_revision>
```

Переименование текущей ветки:

```bash
git branch -m <new_branch_name>
```

Если ветка с новым именем уже существует, для принудительного переименования
используется параметр `-M`. Перед его применением нужно убедиться, что
существующая ветка с таким именем не содержит нужных коммитов.

Безопасное удаление локальной ветки, уже объединённой с текущей:

```bash
git branch -d <branch_name>
```

Принудительное удаление локальной ветки:

```bash
git branch -D <branch_name>
```

Перед `git branch -D` следует проверить, что нужные коммиты не будут потеряны.

## Слияние веток

Слияние выбранной ветки с текущей:

```bash
git merge <branch_name>
```

Git добавляет изменения указанной ветки в ту ветку, которая активна сейчас.
Поэтому перед слиянием нужно проверить текущую ветку командой `git status`.

Если текущая ветка не содержит собственных новых коммитов, Git может выполнить
`fast-forward`. В этом случае указатель ветки передвигается вперёд без создания
отдельного merge-коммита.

Создание merge-коммита даже при возможности `fast-forward`:

```bash
git merge --no-ff <branch_name>
```

Отмена незавершённого слияния:

```bash
git merge --abort
```

## Rebase

Перенос коммитов текущей ветки на вершину другой ветки:

```bash
git rebase <base_branch>
```

`rebase` создаёт новые версии переносимых коммитов и делает историю линейной.
Идентификаторы этих коммитов изменяются.

Интерактивное редактирование нескольких последних коммитов:

```bash
git rebase -i HEAD~<number>
```

Интерактивный режим позволяет менять порядок коммитов, объединять их, изменять
сообщения и удалять ненужные коммиты.

Продолжение после разрешения конфликта:

```bash
git add <resolved_file>
git rebase --continue
```

Отмена выполняемого rebase:

```bash
git rebase --abort
```

Опубликованную общую ветку не следует переписывать через `rebase` без
согласования с другими участниками.

## Удалённые репозитории

Просмотр настроенных удалённых репозиториев:

```bash
git remote -v
```

Добавление удалённого репозитория:

```bash
git remote add origin <repository_url>
```

Получение информации о новых удалённых коммитах без изменения рабочей ветки:

```bash
git fetch origin
```

Получение удалённых изменений и их объединение с текущей веткой:

```bash
git pull
```

В стандартной конфигурации `git pull` сначала выполняет получение данных, затем
слияние с текущей веткой. Перед этой командой желательно проверить состояние
рабочей папки.

Первая отправка локальной ветки:

```bash
git push -u origin <branch_name>
```

Параметр `-u` связывает локальную ветку с удалённой. После этого обычно
достаточно команды:

```bash
git push
```

Удаление ветки из удалённого репозитория:

```bash
git push origin --delete <branch_name>
```

## Временное сохранение изменений

Сохранение отслеживаемых незакоммиченных изменений:

```bash
git stash push -m "Short description"
```

Сохранение вместе с новыми неотслеживаемыми файлами:

```bash
git stash push -u -m "Short description"
```

Просмотр временных сохранений:

```bash
git stash list
```

Применение последнего сохранения без удаления из списка:

```bash
git stash apply
```

Применение последнего сохранения с удалением из списка:

```bash
git stash pop
```

Удаление выбранного сохранения:

```bash
git stash drop <stash_name>
```

`stash` удобен для временного освобождения рабочей папки. Он не заменяет коммит
для законченного изменения.

## Перенос отдельных коммитов

Перенос одного выбранного коммита в текущую ветку:

```bash
git cherry-pick <commit_hash>
```

Перенос нескольких выбранных коммитов:

```bash
git cherry-pick <first_hash> <second_hash>
```

Git применяет изменение и создаёт в текущей ветке новый коммит с новым
идентификатором.

Продолжение после разрешения конфликта:

```bash
git add <resolved_file>
git cherry-pick --continue
```

Отмена выполняемого переноса:

```bash
git cherry-pick --abort
```

## Отмена изменений

Способ отмены зависит от того, где находится изменение и опубликовано ли оно.

### Изменение ещё не добавлено в индекс

Восстановление файла до состояния последнего коммита:

```bash
git restore path/to/file.py
```

Незакоммиченные изменения файла будут потеряны.

### Изменение уже добавлено в индекс

Удаление файла из индекса с сохранением изменений в рабочей папке:

```bash
git restore --staged path/to/file.py
```

### Коммит уже опубликован

Создание нового коммита, отменяющего изменение выбранного коммита:

```bash
git revert <commit_hash>
```

`revert` сохраняет существующую историю и обычно подходит для общей ветки.

### Локальные коммиты нужно удалить из истории

Перемещение ветки с сохранением изменений в индексе:

```bash
git reset --soft <commit_hash>
```

Перемещение ветки с сохранением изменений только в рабочей папке:

```bash
git reset --mixed <commit_hash>
```

Перемещение ветки с удалением последующих изменений из рабочей папки:

```bash
git reset --hard <commit_hash>
```

`reset` изменяет положение текущей ветки. Вариант `--hard` может удалить
незакоммиченные изменения и требует особой осторожности.

## Принудительная отправка изменённой истории

После `rebase`, `reset` или `commit --amend` идентификаторы опубликованных
коммитов могут измениться. Обычный `git push` в таком случае будет отклонён.

Для обновления собственной ветки используется:

```bash
git push --force-with-lease
```

`--force-with-lease` проверяет, не появились ли в удалённой ветке неизвестные
локальному репозиторию изменения. Это безопаснее, чем `--force`, но общую ветку
всё равно нельзя переписывать без согласования с командой.

## Разрешение конфликтов

Конфликт возникает, когда Git не может автоматически объединить изменения.
Конфликтующий участок файла содержит маркеры:

```text
<<<<<<< HEAD
содержимое текущей ветки
=======
содержимое присоединяемой ветки
>>>>>>> branch-name
```

Для разрешения конфликта нужно:

1. Открыть конфликтующий файл.
2. Выбрать или составить правильное итоговое содержимое.
3. Удалить служебные маркеры конфликта.
4. Проверить работу файла.
5. Выполнить `git add <resolved_file>`.
6. Продолжить или завершить текущую операцию.

Список конфликтующих файлов показывает команда:

```bash
git status
```

## Игнорирование файлов

Файл `.gitignore` перечисляет пути, которые Git не должен добавлять в
репозиторий. Пример:

```gitignore
.venv/
__pycache__/
*.pyc
.env
data/
models/
```

`.gitignore` не действует на файл, который уже отслеживается. Удалить такой файл
только из индекса можно командой:

```bash
git rm --cached path/to/file
```

Секреты, пароли, токены и приватные ключи нельзя коммитить даже в учебный
репозиторий.

## Теги

Создание аннотированного тега:

```bash
git tag -a v1.0.0 -m "Version 1.0.0"
```

Просмотр тегов:

```bash
git tag
```

Отправка выбранного тега:

```bash
git push origin v1.0.0
```

Теги обычно используются для обозначения выпущенных версий проекта.

## Восстановление потерянного коммита

Журнал перемещений указателей Git:

```bash
git reflog
```

`reflog` помогает найти прежний идентификатор коммита после ошибочного
`reset`, `rebase` или переключения ветки. Найденный коммит можно сохранить в
новой ветке:

```bash
git branch <recovery_branch> <commit_hash>
```

## Выбор подходящей команды

| Ситуация | Подходящая команда |
|---|---|
| Посмотреть текущее состояние | `git status` |
| Посмотреть несохранённые изменения | `git diff` |
| Подготовить изменение к коммиту | `git add` |
| Сохранить версию в истории | `git commit` |
| Начать отдельную работу | `git switch -c` |
| Объединить две ветки | `git merge` |
| Временно убрать незаконченную работу | `git stash` |
| Перенести один выбранный коммит | `git cherry-pick` |
| Безопасно отменить опубликованный коммит | `git revert` |
| Изменить локальную историю | `git reset` или `git rebase` |
| Получить сведения об удалённых изменениях | `git fetch` |
| Получить и объединить удалённые изменения | `git pull` |
| Отправить локальные коммиты | `git push` |
| Найти потерянное состояние | `git reflog` |

## Полезная последовательность проверки

Перед сложной операцией:

```bash
git status
git branch -vv
git log --graph --oneline --all --decorate
```

После операции выполните те же команды и убедитесь, что:

- активна нужная ветка;
- рабочая папка находится в ожидаемом состоянии;
- нужные коммиты присутствуют в истории;
- удалённая и локальная ветки не разошлись неожиданным образом.
