# Практика 6. ML-сервис на FastAPI

## Цель

Разработать HTTP API для классификации объектов Iris. Сервис должен загружать
заранее обученную модель, проверять входные данные, возвращать предсказание и
иметь автоматические тесты контракта. Соберите отдельный Docker-образ сервиса.

## Исходные данные

Продолжайте работу в репозитории [практики 5](../practice_5/docker_practice.md).
Используйте `iris_random_forest.joblib` и `metrics.json` из одного запуска
обучающего контейнера.

Сервис ищет оба файла в каталоге, заданном переменной `MODEL_DIR`.
Для локального запуска из корня репозитория используйте каталог
`models`. В контейнере задайте `MODEL_DIR=/app/models`.

При старте приложения загрузите модель через `joblib` и прочитайте
`model_version`, `classes` и `feature_names` из `metrics.json`. Каждый запрос
использует уже загруженную модель.

## Структура проекта

```text
app/
  main.py
  api.py
  schemas.py
  model_service.py
models/
  iris_random_forest.joblib
  metrics.json
tests/
  test_api.py
Dockerfile
```

Допускается другая структура, если обязанности модулей разделены и команда
запуска указана в README.

Дополните общий `pyproject.toml` зависимостями FastAPI и Uvicorn. Добавьте
`httpx` в группу `test` для работы `TestClient`. Обновите `poetry.lock` и
используйте его в обоих образах. Так версия scikit-learn при обучении и
загрузке модели будет совпадать.

Каталог `models/` создаётся при обучении и остаётся вне Git и контекста
сборки. Файлы из этого каталога подключаются при запуске сервиса.

## Контракт API

### `GET /health`

Успешный ответ имеет код `200` и содержит:

```json
{
  "status": "ok",
  "model_version": "1.0.0"
}
```

Сервис не должен отвечать `ok`, если обязательный файл модели не загрузился.

### `POST /api/v1/predict`

Тело запроса:

```json
{
  "sepal_length": 5.1,
  "sepal_width": 3.5,
  "petal_length": 1.4,
  "petal_width": 0.2
}
```

Успешный ответ имеет код `200` и содержит:

- числовой класс;
- строковое имя класса;
- вероятности всех классов;
- версию модели;
- время обработки в миллисекундах.

Сумма вероятностей должна отличаться от `1.0` не более чем на `1e-6`.
Перед вызовом модели расположите признаки в порядке из `feature_names`.
Для Iris это `sepal_length`, `sepal_width`, `petal_length`, `petal_width`.
Порядок вероятностей должен совпадать с порядком классов в `metrics.json`.

Пример успешного ответа:

```json
{
  "predicted_class": 0,
  "class_name": "setosa",
  "probabilities": [0.97, 0.02, 0.01],
  "model_version": "1.0.0",
  "latency_ms": 1.25
}
```

Числа вероятностей и `latency_ms` в примере не являются ожидаемыми точными
значениями. Они зависят от обученной модели и среды выполнения.

### `POST /api/v1/predict-batch`

Метод принимает от 1 до 64 объектов. Модель вызывается один раз для всего
батча. Ответ сохраняет порядок входных объектов.

Тело запроса:

```json
{
  "items": [
    {
      "sepal_length": 5.1,
      "sepal_width": 3.5,
      "petal_length": 1.4,
      "petal_width": 0.2
    },
    {
      "sepal_length": 6.3,
      "sepal_width": 3.3,
      "petal_length": 6.0,
      "petal_width": 2.5
    }
  ]
}
```

Ответ должен иметь следующую структуру:

```json
{
  "predictions": [
    {
      "predicted_class": 0,
      "class_name": "setosa",
      "probabilities": [0.97, 0.02, 0.01]
    },
    {
      "predicted_class": 2,
      "class_name": "virginica",
      "probabilities": [0.01, 0.04, 0.95]
    }
  ],
  "model_version": "1.0.0",
  "latency_ms": 1.8
}
```

Поля `model_version` и `latency_ms` относятся ко всему батчу. Элементы
`predictions` располагаются в том же порядке, что и элементы `items` во
входном JSON. Числа в примере показывают только форму ответа.

## Валидация

Pydantic-схемы должны проверять:

- наличие всех четырёх признаков;
- числовой тип;
- положительное значение каждого признака;
- размер батча;
- отсутствие неизвестных полей.

Некорректные данные должны возвращать `422` до вызова модели.

Чтобы неизвестные поля не игнорировались, задайте для входных моделей
`ConfigDict(extra="forbid")`. Например, поле `color` в объекте Iris должно
привести к ответу `422`.

## Обработка ошибок

Требования:

- отсутствие файла модели при старте завершает запуск с понятной ошибкой;
- ошибка инференса не возвращает traceback клиенту;
- ожидаемые ошибки имеют явный HTTP-код и поле `detail`;
- секреты и абсолютные локальные пути не попадают в ответ.

Полный traceback непредвиденной ошибки записывается в серверный лог. Клиенту
возвращается код `500` и нейтральное сообщение, например
`{"detail": "Inference failed"}`.

## Документация

Swagger UI должен быть доступен по `/docs`, OpenAPI JSON по `/openapi.json`.

Для каждого маршрута задайте:

- краткое назначение;
- response model;
- возможные коды ответа;
- пример входных данных.

В README добавьте минимум по одному готовому примеру запроса к `/health`,
`/api/v1/predict` и `/api/v1/predict-batch`. Можно использовать `curl` или
Python с библиотекой `httpx`.

## Автоматические тесты

Используйте `pytest` и `TestClient`.

Обязательные сценарии:

1. `/health` возвращает `200` и версию модели.
2. Класс одиночного предсказания совпадает с прямым вызовом модели, а
   вероятности совпадают с точностью `1e-6`.
3. Вероятности имеют правильную длину и сумму.
4. Батч из нескольких объектов сохраняет порядок.
5. Пустой батч возвращает `422`.
6. Батч из 65 объектов возвращает `422`.
7. Пропущенный признак возвращает `422`.
8. Отрицательное значение возвращает `422`.
9. Неизвестное поле возвращает `422`.
10. `/docs` и `/openapi.json` доступны.

Тесты не должны обращаться к внешней сети.
В фикстуре pytest запустите обучение из `train_model.py` с выходным путём во
временный каталог. Передайте путь к этому каталогу через `MODEL_DIR` до
запуска приложения в `TestClient`.
Тогда `pytest` можно запустить из чистого клона без Docker и локальных
файлов модели.

## Запуск

Для локального запуска используйте файлы из bind mount практики 5. Из
корня репозитория выполните следующие команды.

```bash
poetry install --with test --no-root
poetry run python -m pytest -q
poetry run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

## Запуск сервиса в Docker

Создайте корневой `Dockerfile` для сервиса. Используйте Python 3.12 и
устанавливайте основные зависимости из общего `poetry.lock`. Приложение
должно запускаться от пользователя без прав `root` и слушать
`0.0.0.0:8000` внутри контейнера.

Соберите образ и подключите volume `iris-models` из практики 5 к
`/app/models` в режиме только для чтения. Опубликуйте порт контейнера и
проверьте с хоста `/health`, `/api/v1/predict` и `/docs`. Ответы
`/health` и `/api/v1/predict` должны содержать версию из `metrics.json`.
Добавьте в README команды сборки, запуска и проверки запросов.

## Результат этапа

В общем репозитории появляются следующие файлы.

- исходный код сервиса;
- `Dockerfile` для запуска сервиса;
- тесты HTTP API;
- обновлённые `pyproject.toml` и `poetry.lock`;
- команды запуска сервиса и примеры запросов в README.

В репозитории не должно быть виртуального окружения, кэша, логов и локальных
временных файлов.

| Корректный `/health` | 5 |

| Батч-инференс одним вызовом модели | 10 |
| Pydantic-валидация | 10 |

Дополнительная часть даёт до 20 баллов. Итоговая оценка не превышает 100.

| Дополнительное задание | Баллы |
|---|---:|
| Структурированные логи с request ID | 5 |
| Метрики количества запросов и latency | 5 |
| Docker HEALTHCHECK | 5 |
| Нагрузочный тест с анализом результатов | 5 |

Для зачёта дополнительных пунктов требуется не только код:

- для логов покажите один запрос и соответствующую запись с request ID;
- для метрик укажите endpoint и приведите пример значений счётчика и latency;
- для Docker HEALTHCHECK покажите, что контейнер получает статус `healthy`;
- для нагрузочного теста сохраните команду запуска, число запросов, уровень
  параллелизма, latency и долю ошибок.

## Работа не принимается

- модель обучается при каждом HTTP-запросе;
- тестовые данные используются для обучения;
- сервис принимает произвольное число признаков без проверки;
- пароль, токен или другой секрет находится в исходном коде;
- модель нельзя загрузить в чистом окружении;
- тесты зависят от порядка запуска;
- единственным подтверждением работы является скриншот Swagger UI.
