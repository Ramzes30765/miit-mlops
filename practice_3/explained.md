# Версионирование данных с DVC и ClearML

Код проекта обычно хранится в Git, но наборы данных могут быть слишком большими
для обычного Git-репозитория. DVC и ClearML Dataset решают эту проблему разными
способами.

Этот файл является самостоятельным справочником. Он объясняет основные понятия
и команды, но не содержит пошагового решения практической работы.

## Зачем версионировать данные

Версия модели зависит не только от кода и гиперпараметров. На результат также
влияют:

- исходные файлы;
- train, validation и test split;
- очистка данных;
- порядок и правила преобразований;
- версия библиотек;
- добавленные и удалённые объекты.

Фраза «использовался тот же датасет» недостаточна. Для воспроизводимости нужен
идентификатор конкретного состояния данных и способ получить его повторно.

## Хэш и идентификатор версии

Хэш вычисляется из содержимого файла. Если содержимое меняется, меняется и хэш.
Имя файла при этом может остаться прежним.

Хэш полезен для:

- проверки целостности;
- определения изменившихся файлов;
- дедупликации одинакового содержимого;
- связи метаданных с конкретным состоянием данных.

Хэш сам по себе не объясняет происхождение данных, лицензию, назначение столбцов
или причину изменения. Эти сведения нужно хранить отдельно в описании версии.

## Общая модель версионирования

В обоих подходах можно выделить четыре части:

1. Рабочая копия данных на компьютере.
2. Метаданные версии.
3. Хранилище содержимого.
4. Операция восстановления выбранной версии.

DVC сохраняет метаданные рядом с Git-проектом, а содержимое помещает в DVC
cache и remote. ClearML хранит версию как отдельный Dataset с ID, метаданными,
lineage и ссылками на файлы в настроенном storage.

# DVC

## Основные компоненты DVC

| Компонент | Что содержит |
|---|---|
| Workspace | Текущие файлы данных, с которыми работает пользователь |
| `.dvc`-файл | Хэш, размер и путь отслеживаемых данных |
| DVC cache | Локальное содержимое известных версий данных |
| DVC remote | Общее хранилище данных для других машин и пользователей |
| Git | Историю `.dvc`-файлов, конфигурации и исходного кода |

Git не хранит сами большие файлы данных. Он хранит небольшие DVC-метафайлы,
которые указывают на нужное содержимое.

## Инициализация

Внутри Git-репозитория:

```bash
dvc init
```

Команда создаёт служебную директорию `.dvc` и `.dvcignore`. Эти файлы нужно
сохранить в Git.

Проверка состояния:

```bash
git status
dvc status
```

`git status` показывает изменения метаданных и кода. `dvc status` показывает
расхождение между DVC-метаданными, cache и workspace.

## Добавление данных

```bash
dvc add data
```

После команды:

- содержимое `data` сохраняется в DVC cache;
- создаётся или обновляется `data.dvc`;
- директория `data` добавляется в `.gitignore`;
- `data.dvc` и `.gitignore` нужно сохранить в Git.

`dvc add` не создаёт Git-коммит и не отправляет данные в remote.

## Изменение уже отслеживаемых данных

После изменения файлов в отслеживаемой директории можно снова выполнить:

```bash
dvc add data
```

DVC пересчитает состояние директории и обновит `data.dvc`. Затем метафайл
сохраняют отдельным Git-коммитом.

Команда `dvc commit` также умеет принимать изменения уже отслеживаемых outputs,
но она чаще нужна в специальных сценариях ручного изменения output или запуска
с `--no-commit`. Для базового учебного сценария повторный `dvc add` понятнее.

Если `dvc commit` вызывается с целью, целью обычно является `.dvc`-файл или
stage, а не путь внутри отслеживаемой директории.

## DVC remote

Локальный cache не доступен на другом компьютере. Для обмена данными нужен DVC
remote.

Remote может находиться:

- в локальной или сетевой директории;
- в S3-совместимом storage;
- в Google Cloud Storage;
- в Azure Blob Storage;
- в SSH-хранилище;
- в другом поддерживаемом backend.

Добавление remote:

```bash
dvc remote add -d storage <remote_url_or_path>
```

Флаг `-d` делает remote используемым по умолчанию. Обычная конфигурация
сохраняется в `.dvc/config` и может быть добавлена в Git, если не содержит
секретов.

Локальные credentials и пользовательские настройки сохраняют отдельно:

```bash
dvc remote modify --local storage <parameter> <value>
```

Локальная конфигурация не должна попадать в Git.

## Push и pull

Отправка известных объектов из cache в remote:

```bash
dvc push
```

Получение недостающих объектов из remote и восстановление workspace:

```bash
dvc pull
```

`git push` отправляет код и DVC-метаданные. `dvc push` отправляет содержимое
данных. Для полного воспроизведения проекта обычно нужны обе операции.

## Переключение версии

После переключения Git-ветки или коммита меняется `data.dvc`, но содержимое
workspace не обязано измениться автоматически.

```bash
git switch <branch>
dvc checkout
```

`dvc checkout` приводит DVC-tracked файлы в соответствие с текущими
метаданными Git. Нужная версия должна присутствовать в cache. Если её нет,
сначала используют `dvc pull`.

Типичный порядок восстановления:

```bash
git clone <repository_url>
cd <repository_directory>
dvc pull
```

## Ветки и слияние

Ветки данных соответствуют Git-веткам, потому что каждая ветка хранит свою
версию `.dvc`-файла.

Если две ветки изменили один `.dvc`-файл, Git может обнаружить конфликт. Для
директорий DVC предоставляет merge driver:

```bash
git config merge.dvc.name "DVC merge driver"
git config merge.dvc.driver "dvc git-hook merge-driver --ancestor %O --our %A --their %B"
```

В `.gitattributes` добавляют:

```gitattributes
*.dvc merge=dvc
```

Если ветки добавили или изменили разные файлы внутри DVC-директории, merge
driver часто может объединить состояния автоматически.

Если обе ветки по-разному изменили один и тот же файл данных, автоматическое
слияние не определяет правильное содержимое. Нужно:

1. Получить обе версии данных из cache или remote.
2. Сохранить их во временных директориях.
3. Объединить данные по правилам предметной области.
4. Повторно выполнить `dvc add`.
5. Проверить итоговый состав и только затем завершить merge.

Нельзя просто выполнить `dvc add` над текущим workspace, не получив вторую
версию: так можно незаметно потерять изменение другой ветки.

## Проверка версии DVC

Полезные команды:

```bash
dvc status
dvc diff
dvc list .
dvc doctor
```

Также проверяют:

- Git commit;
- хэш в `.dvc`-файле;
- наличие данных в remote;
- список и хэши файлов после чистого восстановления.

# ClearML Dataset

## Основные понятия ClearML Dataset

| Понятие | Назначение |
|---|---|
| Project | Пространство для группировки datasets |
| Dataset name | Общее имя набора версий |
| Dataset version | Человекочитаемый номер версии |
| Dataset ID | Уникальный идентификатор конкретной версии |
| Parent dataset | Родитель, содержимое которого наследуется новой версией |
| Lineage | Граф происхождения версий |
| Storage | Место хранения файлов Dataset |

Для автоматизации надёжнее использовать Dataset ID. Имя и номер версии удобны
для человека, но могут быть введены неоднозначно или повторно.

## Настройка доступа

SDK устанавливается как Python-пакет `clearml`. Подключение к серверу обычно
настраивается через:

```bash
clearml-init
```

API credentials и адреса сервера не добавляют в notebook, Git или отчёт.
Файл конфигурации пользователя также не нужно копировать в репозиторий.

## Жизненный цикл версии

Основной жизненный цикл:

1. Создать mutable Dataset.
2. Добавить или синхронизировать файлы.
3. Загрузить ожидающие файлы в storage.
4. Финализировать Dataset.

```python
from clearml import Dataset

dataset = Dataset.create(
    dataset_project="<project>",
    dataset_name="<name>",
    dataset_version="1.0.0",
    description="Initial version",
)
dataset.add_files(path="data")
dataset.upload()
dataset.finalize()
```

После `finalize()` версия становится immutable. Добавлять файлы в неё больше
нельзя.

Метод `finalize()` не создаёт следующую версию. Он закрывает текущую версию.
Если есть незагруженные файлы, сначала нужен `upload()` либо осознанное
использование `finalize(auto_upload=True)`.

## Создание дочерней версии

Новая версия может наследовать содержимое одной или нескольких предыдущих:

```python
child = Dataset.create(
    dataset_project="<project>",
    dataset_name="<name>",
    dataset_version="1.1.0",
    parent_datasets=[parent_id],
    description="Added new data",
)
```

После этого в child добавляют только новые или изменённые файлы, загружают их и
финализируют версию.

Другой вариант - получить writable copy существующей версии:

```python
child = Dataset.get(dataset_id=parent_id, writable_copy=True)
```

В явной учебной работе `Dataset.create(..., parent_datasets=[...])` нагляднее,
потому что родитель и номер новой версии видны в коде.

## Mutable локальная копия

Финализированную версию можно получить как read-only cache:

```python
path = Dataset.get(dataset_id=dataset_id).get_local_copy()
```

Для редактирования используют отдельную writable директорию:

```python
path = Dataset.get(dataset_id=dataset_id).get_mutable_local_copy(
    target_folder="<empty_target_folder>",
    overwrite=False,
)
```

`target_folder` должен быть пустым или отсутствовать. Использование разных
директорий для разных версий снижает риск случайно изменить не ту копию.

## Синхронизация папки

Если локальная директория должна стать полным состоянием новой версии, удобно
использовать:

```python
dataset.sync_folder(local_path="<folder>")
```

Метод определяет добавленные, изменённые и удалённые файлы относительно
родителей. После синхронизации по-прежнему нужны `upload()` и `finalize()`.

## Получение конкретной версии

Самый однозначный способ:

```python
dataset = Dataset.get(dataset_id="<dataset_id>")
```

Также можно искать по project, name и version:

```python
dataset = Dataset.get(
    dataset_project="<project>",
    dataset_name="<name>",
    dataset_version="1.0.0",
    only_completed=True,
)
```

Поиск только по имени на общем сервере может вернуть не ту версию или Dataset
из другого проекта.

## Проверка состава и lineage

```python
dataset.list_files()
dataset.list_added_files()
dataset.list_modified_files()
dataset.list_removed_files()
dataset.get_dependency_graph()
```

Проверять нужно не только номер версии, но и:

- Dataset ID;
- parent IDs;
- список файлов;
- добавленные и изменённые файлы;
- локальные хэши после скачивания.

## Storage и локальный cache

`upload()` по умолчанию использует ClearML File Server либо storage,
настроенный для проекта и SDK. Можно явно задать `output_uri` при создании или
`output_url` при загрузке.

Web UI показывает метаданные и состояние Dataset, но сам UI не является
названием storage.

Повторный `get_local_copy()` может вернуть данные из локального cache. Это
ускоряет работу, но при проверке воспроизводимости важно отличать успешное
получение из cache от доступности Dataset для другой машины.

## Уникальные имена учебных datasets

На общем ClearML server несколько студентов не должны использовать одно имя
`demo_dataset` в одном project.

Подходящий шаблон:

```text
project: MIIT/MLOps/practice_3/<student_id>
name: sklearn-data-<student_id>
```

В отчёте всё равно сохраняются точные Dataset IDs.

# Датасеты scikit-learn

Scikit-learn содержит небольшие datasets, которые удобно использовать в
учебных примерах без ручного скачивания больших архивов.

Пример получения таблицы:

```python
from sklearn.datasets import load_iris

iris = load_iris(as_frame=True)
frame = iris.frame
```

При сохранении версии нужно определить:

- порядок строк;
- названия и порядок столбцов;
- наличие индекса в CSV;
- правила округления чисел;
- версию scikit-learn и pandas.

Два CSV с одинаковыми значениями могут иметь разные байтовые хэши из-за
форматирования. Поэтому полезно одновременно проверять SHA-256 файла и
семантические свойства таблицы: форму, столбцы, типы и контрольные значения.

# Сравнение DVC и ClearML Dataset

| Свойство | DVC | ClearML Dataset |
|---|---|---|
| История метаданных | Git | ClearML Server |
| Идентификатор версии | Git commit и хэш `.dvc` | Dataset ID и version |
| Локальное хранилище | DVC cache | ClearML cache |
| Общее хранилище | DVC remote | ClearML File Server или внешний storage |
| Ветвление | Git branches | Parent datasets и lineage DAG |
| Восстановление | `dvc pull` и `dvc checkout` | `Dataset.get` и local copy |
| Слияние | Git и DVC merge driver | Несколько parents или новая производная версия |
| UI | Зависит от дополнительного сервиса | ClearML Web UI |

Инструменты не являются полностью взаимозаменяемыми. DVC тесно связывает
данные с Git-историей проекта. ClearML Dataset предоставляет отдельный объект
версии, lineage и интеграцию с экспериментами ClearML.

# Что сохранять в Git

Для DVC:

- `.dvc/` без локальных секретов;
- `.dvcignore`;
- `.dvc`-файлы;
- `.gitattributes`;
- код подготовки данных;
- документацию.

Для ClearML:

- код создания и получения Dataset;
- безопасные project и name шаблоны;
- зависимости;
- документацию;
- Dataset IDs в отчёте или конфигурации конкретного эксперимента.

Не добавляют:

- DVC cache;
- локальный DVC remote внутри проекта;
- скачанные копии datasets;
- ClearML credentials;
- пользовательский `clearml.conf`;
- реальные секреты storage.
