# Практическая работа: версионирование данных с DVC и ClearML

## Цель

Научиться сохранять, переключать, объединять и восстанавливать версии данных
двумя способами:

- с помощью Git, DVC cache и DVC remote;
- с помощью ClearML Dataset, Dataset IDs и lineage.

Перед выполнением изучите [explained.md](explained.md) и выполните
[демонстрационный ноутбук](dvc_clearml_sklearn_demo.ipynb).

Ноутбук использует другие datasets и более простой сценарий. Его результаты
нельзя сдавать вместо самостоятельной работы.

## Исходные данные

В самостоятельной работе используются:

- `load_iris(as_frame=True)`;
- `load_wine(as_frame=True)`.

Оба набора входят в scikit-learn и не требуют отдельного скачивания.

Сохраняйте таблицы в CSV:

- без столбца индекса pandas;
- с неизменным порядком столбцов;
- после детерминированной сортировки по всем исходным признакам и target;
- с одинаковыми параметрами сохранения во всех версиях.

## Общие требования

- Используйте Python 3.12.
- Зафиксируйте версии DVC, ClearML, scikit-learn и pandas.
- Работайте в отдельном Git-репозитории `mlops-data-<your_surname>`.
- Основная ветка называется `main`.
- Не добавляйте CSV, DVC cache, локальный remote и ClearML credentials в Git.
- Не используйте имена `demo_dataset` и `Seminar3` на общем ClearML server.
- Не удаляйте созданные ClearML Dataset до завершения проверки.
- Все Dataset IDs, Git commits и хэши фиксируйте в `REPORT.md`.
- Не изменяйте файлы внутри DVC cache вручную.

## Часть 1. Подготовка таблиц

### 1. Генератор данных

Создайте скрипт `prepare_data.py`. Он должен принимать режим работы и создавать
одну из версий данных.

Поддержите три режима:

1. `base` - сохранить исходный Iris в `data/iris.csv`.
2. `wine` - сохранить исходный Wine в `data/wine.csv`, не изменяя Iris.
3. `iris_features` - добавить в Iris два вычисляемых столбца:
   `sepal_area` и `petal_area`, не добавляя Wine.

Скрипт должен повторно создавать одинаковые байты CSV при одинаковых версиях
Python и зависимостей.

Ожидаемый результат:

- режим `base` создаёт только `iris.csv`;
- режим `wine` добавляет только `wine.csv`;
- режим `iris_features` изменяет только `iris.csv`;
- исходные признаки и target не теряются.

### 2. Проверка данных

Создайте скрипт `check_data.py`, который выводит для каждого CSV:

- относительный путь;
- SHA-256;
- количество строк и столбцов;
- список столбцов;
- число пропущенных значений.

Скрипт должен завершаться ошибкой, если:

- отсутствует ожидаемый файл;
- появился безымянный столбец индекса;
- количество строк отличается от исходного Dataset scikit-learn;
- вычисляемые столбцы содержат неправильные значения.

## Часть 2. DVC

### 3. Базовая версия

1. Инициализируйте Git и DVC.
2. Настройте merge driver DVC для `.dvc`-файлов.
3. Создайте данные в режиме `base`.
4. Начните отслеживать директорию `data` через DVC.
5. Сохраните DVC-метаданные, `.gitignore`, `.gitattributes`, скрипты и файлы
   окружения в Git.
6. Отметьте коммит Git tag `data-v1`.

Ожидаемый результат:

- `data/iris.csv` существует в workspace;
- `data/wine.csv` отсутствует;
- в Git нет CSV;
- в Git находится `data.dvc`;
- `dvc status` не показывает несохранённых изменений.

### 4. DVC remote

Создайте DVC remote в отдельной локальной директории вне Git-репозитория.
Сохраните безопасную конфигурацию remote в Git и отправьте базовую версию
данных.

Ожидаемый результат:

- DVC remote не находится внутри сдаваемого репозитория;
- данные базовой версии присутствуют в remote;
- удаление локального cache не делает версию невосстановимой.

### 5. Ветка с Wine

1. Создайте от `main` ветку `feature/wine`.
2. Запустите генератор в режиме `wine`.
3. Обновите состояние DVC.
4. Сохраните изменение `data.dvc` отдельным Git-коммитом.
5. Отправьте новые объекты в DVC remote.

Ожидаемый результат ветки:

- присутствуют `iris.csv` и `wine.csv`;
- `iris.csv` имеет тот же SHA-256, что в `data-v1`;
- `data.dvc` отличается от `main`;
- Git-коммит не содержит сами CSV.

### 6. Ветка с новыми признаками Iris

1. Вернитесь в `main`.
2. Приведите workspace в соответствие с `main` средствами DVC.
3. Убедитесь, что `wine.csv` исчез, а Iris вернулся к базовой версии.
4. Создайте ветку `feature/iris-features`.
5. Запустите генератор в режиме `iris_features`.
6. Обновите DVC-метаданные и сохраните их отдельным Git-коммитом.
7. Отправьте новые объекты в DVC remote.

Ожидаемый результат ветки:

- `wine.csv` отсутствует;
- `iris.csv` содержит `sepal_area` и `petal_area`;
- значения новых столбцов равны произведению соответствующих исходных
  размеров;
- исходные строки и target сохранились.

### 7. Объединение веток данных

Находясь в `feature/iris-features`, объедините изменения `feature/wine`.
Используйте настроенный DVC merge driver.

После слияния восстановите итоговый workspace и выполните `check_data.py`.

Ожидаемый результат:

- итоговая версия содержит два CSV;
- `iris.csv` содержит вычисляемые столбцы;
- `wine.csv` совпадает с версией из `feature/wine`;
- Git history сохраняет историю обеих веток;
- `data.dvc` не содержит маркеров конфликта;
- все объекты итоговой версии отправлены в DVC remote.

Если merge driver не может объединить версии автоматически, получите обе
версии данных из cache или remote, объедините их в отдельной временной
директории, проверьте результат и только после этого обновите `data.dvc`.
Фиксация только текущего workspace без проверки второй версии не допускается.

### 8. Чистое восстановление

1. Объедините проверенную ветку в `main`.
2. Клонируйте репозиторий в новую директорию.
3. Не копируйте старый workspace и cache вручную.
4. Получите данные из DVC remote.
5. Запустите `check_data.py`.

Ожидаемый результат: чистый clone восстанавливает оба CSV с теми же SHA-256,
формой и столбцами, что итоговая версия исходного репозитория.

## Часть 3. ClearML Dataset

### 9. Уникальные имена

Используйте:

```text
project: MIIT/MLOps/practice_3/<your_surname>
dataset name: sklearn-tabular-<your_surname>
```

Не записывайте API credentials в код. Перед началом убедитесь, что SDK подключён
к нужному ClearML server.

### 10. Базовый Dataset

Создайте Dataset version `1.0.0` из состояния `base`.

Требования:

- явно указаны project, name и version;
- в описании указано, что версия содержит исходный Iris;
- к версии добавлен тег `base`;
- файлы загружены до финализации;
- финализированная версия содержит только `iris.csv`.

Запишите Dataset ID как `BASE_ID` в отчёт.

Ожидаемый результат: Dataset имеет статус Completed, его можно получить по ID и
скачать на другую машину.

### 11. Дочерняя версия с Wine

Создайте version `1.1.0`, указав `BASE_ID` единственным parent.

Добавьте `wine.csv`, но не загружайте вторую независимую копию неизменённого
`iris.csv` без необходимости.

Запишите Dataset ID как `WINE_ID`.

Ожидаемый результат:

- parent версии `1.1.0` равен `BASE_ID`;
- полный состав версии содержит `iris.csv` и `wine.csv`;
- список добавленных файлов содержит `wine.csv`;
- базовая версия не изменилась.

### 12. Отдельная ветвь lineage

Снова используйте `BASE_ID`, а не `WINE_ID`, как parent. Создайте version
`2.0.0` с состоянием `iris_features`.

Запишите Dataset ID как `IRIS_FEATURES_ID`.

Ожидаемый результат:

- parent версии `2.0.0` равен `BASE_ID`;
- версия содержит изменённый `iris.csv` без `wine.csv`;
- список modified files содержит `iris.csv`;
- `WINE_ID` не является предком новой версии;
- версии `1.1.0` и `2.0.0` образуют две ветви от базы.

### 13. Скачивание и проверка

Получите все три версии строго по Dataset ID и скачайте их в три разные пустые
директории.

Для каждой версии сохраните:

- Dataset ID;
- version;
- parent IDs;
- полный список файлов;
- added, modified и removed files относительно parent;
- SHA-256 каждого скачанного файла;
- форму и столбцы таблиц.

Ожидаемый результат: локальный состав каждой версии совпадает с её описанием и
не зависит от того, какая версия была создана последней.

## Часть 4. Сравнение

### 14. Сравнительная таблица

Добавьте в `REPORT.md` таблицу минимум со следующими строками:

- идентификатор версии;
- расположение метаданных;
- расположение файлов;
- способ создания дочерней версии;
- способ переключения версии;
- способ восстановления на чистой машине;
- поведение при ветвлении;
- поведение при слиянии;
- связь версии данных с Git;
- доступность через UI.

Для каждого утверждения приведите наблюдение из выполненной работы, а не только
определение из справочника.

### 15. Вывод

Ответьте в отчёте:

1. Какой объект однозначно определяет версию данных в DVC?
2. Почему одного Git-коммита недостаточно без DVC remote?
3. Чем Dataset version отличается от Dataset ID в ClearML?
4. Почему `finalize()` нельзя считать созданием следующей версии?
5. Как доказать, что ClearML version `2.0.0` создана от базы, а не от `1.1.0`?
6. Что произойдёт, если после `git switch` не выполнить DVC checkout?
7. В каком сценарии этой работы удобнее DVC, а в каком ClearML Dataset?

## Отчёт

- версии Python, DVC, ClearML, scikit-learn и pandas;
- ссылку на Git-репозиторий;
- Git commits и tags версий DVC;
- хэши `data.dvc` и всех итоговых CSV;
- адрес или описание DVC remote без секретов;
- результат восстановления из чистого clone;
- `BASE_ID`, `WINE_ID` и `IRIS_FEATURES_ID`;

- сравнительную таблицу;

Не вставляйте credentials, полный `clearml.conf` и полные логи команд.

## Что нужно сдать

```text
mlops-data-<your_surname>/
  .dvc/
    config
  .dvcignore
  .gitattributes
  .gitignore
  data.dvc
  prepare_data.py
  check_data.py
  pyproject.toml

  REPORT.md
```

Директорию `data`, DVC cache, локальный DVC remote, скачанные копии ClearML и
credentials сдавать не нужно.

## Критерии проверки

| Раздел | Баллы |
|---|---:|
| Детерминированная подготовка и проверка таблиц | 2 |
| DVC versions, remote и переключение веток | 2 |
| Корректное слияние и чистое восстановление DVC | 2 |
| Три ClearML versions и правильный lineage | 2 |
| Скачивание, хэши, сравнение и отчёт | 2 |

Работа не считается воспроизводимой, если итоговые данные доступны только в
старом локальном cache или только в рабочей директории автора.
