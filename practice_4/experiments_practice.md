# Практическая работа: управление экспериментами

## Цель

Настроить воспроизводимое сравнение моделей в MLflow и зарегистрировать лучший
запуск в ClearML.

Перед выполнением изучите [explained.md](explained.md) и выполните
[демонстрационный notebook](experiments.ipynb).

В демонстрации используется Breast Cancer Dataset. В самостоятельной работе
используйте Wine Dataset. Копирование результатов демонстрации не считается
выполнением задания.

## Исходные данные

Загрузите данные через `sklearn.datasets.load_wine(as_frame=True)`.

Разделите данные на train, validation и test. Требования:

- доли составляют 60, 20 и 20 процентов;
- используется стратификация по target;
- `random_state` имеет одно значение во всех запусках;
- test не участвует в подборе модели;
- состав split сохраняется между запусками.

## Часть 1. Окружение

Создайте отдельное окружение и зафиксируйте зависимости. Подготовьте
`requirements.txt` или `pyproject.toml` с lock-файлом.

Проверка:

```bash
python --version
python -m pip check
```

В отчёте укажите версию Python и версии MLflow, ClearML и scikit-learn.

## Часть 2. MLflow

### 1. Experiment

Создайте experiment с именем:

```text
miit-mlops-practice-4-<surname>
```

Настройте локальный tracking URI или используйте выданный преподавателем
MLflow server. Код должен корректно обрабатывать повторный запуск, когда
experiment уже существует.

### 2. Базовая модель

Обучите Logistic Regression в составе Pipeline со StandardScaler.

Запишите в MLflow:

- тип модели;
- `C`, `solver`, `max_iter` и `random_state`;
- `accuracy`, `precision_weighted`, `recall_weighted` и `f1_weighted` на validation;
- время обучения;
- signature;
- пять строк входного примера;
- модель как artifact `model`.

### 3. Сравнение конфигураций

Проведите не менее шести запусков:

- не менее трёх конфигураций Logistic Regression;
- не менее трёх конфигураций Random Forest;
- параметры моделей должны различаться содержательно;
- набор метрик должен быть одинаковым во всех запусках.

Каждому run задайте понятное имя и тег `model_family`.

### 4. Выбор модели

Получите таблицу запусков через `mlflow.search_runs`. Отсортируйте её по
`f1_weighted` на validation.

Выберите лучший run. Только после выбора рассчитайте метрики на test. Запишите
test-метрики в выбранный run с префиксом `test_`.

В отчёте приведите таблицу минимум со следующими столбцами:

| Столбец | Содержание |
|---|---|
| run ID | Идентификатор запуска |
| model family | Тип модели |
| основные параметры | Параметры, которые сравнивались |
| validation F1 | Метрика выбора |
| training time | Время обучения |

### 5. Проверка модели

Загрузите лучшую модель по URI `runs:/<run_id>/model`.

Проверьте:

- модель принимает test с исходными именами столбцов;
- предсказания исходной и загруженной модели совпадают;
- signature присутствует;
- run содержит все обязательные параметры и метрики.

Сохраните результат проверки в `verification.json` и добавьте его к лучшему run
как artifact.

## Часть 3. ClearML

Настройте ClearML через `clearml-init` или переменные окружения. Подставьте свои
ключи в локальную конфигурацию. Не записывайте значения ключей в сдаваемые
файлы.

Создайте Task:

```text
project: MIIT/MLOps/practice_4/<surname>
task: wine-best-model
```

В Task должны находиться:

- параметры лучшей конфигурации;
- validation и test метрики;
- `verification.json`;
- таблица сравнения запусков;
- файл модели;
- тег с MLflow run ID.

Зарегистрируйте файл модели через `OutputModel`. Укажите framework, имя модели,
метки классов и MLflow run ID в metadata. Опубликуйте модель после проверки.

## Часть 4. Воспроизводимость

Создайте `run_experiments.py`, который выполняет MLflow часть без notebook.

Скрипт должен:

- принимать tracking URI через аргумент или переменную окружения;
- создавать experiment при отсутствии;
- повторять все шесть запусков;
- выбирать лучший run по validation;
- оценивать выбранную модель на test;
- печатать experiment ID, лучший run ID и test F1;
- завершаться с ненулевым кодом при неполном логировании.

Повторный запуск скрипта создаёт новые runs, но не новый experiment с другим
именем.

## Что сдавать

Сдаётся Git-репозиторий со следующими файлами:

```text
run_experiments.py
requirements.txt или pyproject.toml и lock-файл
verification.json
REPORT.md
```

В `REPORT.md` должны быть:

- схема split;
- адрес MLflow и experiment ID;
- таблица запусков;
- обоснование выбора лучшей модели;
- лучший MLflow run ID;
- ClearML Task ID;
- ClearML Model ID;
- test-метрики;
- команда запуска проекта в чистом окружении.

Скриншот без ID и воспроизводимого кода не подтверждает выполнение.

## Критерии оценки

Обязательная часть даёт до 80 баллов.

| Критерий | Баллы |
|---|---:|
| Воспроизводимое окружение и корректный split | 10 |
| Шесть корректно оформленных MLflow runs | 20 |
| Единые параметры, метрики, теги и signature | 15 |
| Выбор по validation и однократная оценка на test | 10 |
| Загрузка модели и автоматическая проверка предсказаний | 10 |
| ClearML Task и опубликованный OutputModel | 10 |
| Полный REPORT.md с идентификаторами | 5 |

Дополнительная часть даёт до 20 баллов. Общая оценка не превышает 100.

| Дополнительное задание | Баллы |
|---|---:|
| Автоматические тесты структуры runs | 5 |
| Матрица ошибок и per-class метрики как artifacts | 5 |
| Запуск MLflow Tracking Server с отдельным backend store | 5 |
| Анализ времени обучения и качества с выводом | 5 |

## Ошибки, при которых работа не принимается

- credentials находятся в Git;
- notebook работает только после запуска ячеек в произвольном порядке;
- experiment или run ID вписан в код вручную;
- модели сравниваются по разным split;
- лучшая модель выбирается по test;
- модель сохранена, но не загружается;
- ClearML Task не содержит идентификатор связанного MLflow run;
- отчёт не позволяет найти созданные сущности.
