# Курсовой проект по дисциплине "Операционализация моделей машинного обучения"

## 1. Цель проекта

Нужно подготовить воспроизводимый ML-проект, который включает обучение или
выбор модели, учёт экспериментов, версионирование данных, HTTP-сервис инференса
и запуск сервиса в Docker.

Проверяется не только наличие файлов, но и возможность повторить заявленный
результат из зафиксированной версии репозитория.

Тему, датасет и тип модели студент выбирает самостоятельно. Допускаются задачи
классификации, регрессии, детекции, сегментации, обработки текста и другие
задачи машинного обучения.

## 2. Общие требования

- Проект хранится в отдельном Git-репозитории.
- Основная ветка называется `main`.
- Для сдачи создаётся итоговый Git tag `v1.0.0` или другой согласованный
  версионный tag.
- Указанный tag должен однозначно определять исходный код, конфигурацию и
  версию модели.
- Используется Python с явно указанной поддерживаемой версией.
- Зависимости восстанавливаются из файлов проекта и lock-файла.
- Директории виртуальных окружений, кэши, локальные датасеты и секреты не
  добавляются в Git.
- Все токены, пароли и ключи передаются через переменные окружения или
  хранилище секретов.
- В репозитории должен находиться `.env.example` или другой шаблон настроек без
  реальных секретов.
- Основной сценарий проекта должен запускаться по инструкции из `README.md`.
- Все ссылки в документации должны быть доступны преподавателю на момент
  проверки.

## 3. Обязательные компоненты - 80 баллов

### 3.1. Git и воспроизводимое окружение - 10 баллов

Требования:

- репозиторий содержит осмысленную историю коммитов;
- изменения разрабатываются в отдельных ветках и попадают в `main` через
  merge request или pull request;
- в репозитории есть корректный `.gitignore`;
- указана поддерживаемая версия Python;
- зависимости описаны в `pyproject.toml` или аналогичном файле;
- точные версии зафиксированы lock-файлом;
- чистое окружение можно восстановить без ручной установки отдельных пакетов;
- итоговая версия отмечена Git tag.

Проверяемый результат:

- преподаватель клонирует итоговый tag;
- создаёт новое окружение по инструкции;
- устанавливает зависимости из файлов проекта;
- получает рабочие команды обучения, тестирования и запуска сервиса.

Баллы:

| Критерий | Баллы |
|---|---:|
| История Git, ветки и итоговый tag | 3 |
| Корректный `.gitignore` и отсутствие локальных файлов | 2 |
| `pyproject.toml`, версия Python и lock-файл | 3 |
| Проверенная инструкция восстановления окружения | 2 |

### 3.2. Docker - 15 баллов

Требования:

- сервис инференса собирается с помощью `Dockerfile`;
- image собирается из зафиксированного базового image;
- тег `latest` не используется как единственный идентификатор;
- зависимости устанавливаются воспроизводимым способом;
- приложение внутри контейнера запускается не от имени `root`;
- присутствует `.dockerignore`;
- модель и необходимые runtime-файлы доступны контейнеру описанным в
  документации способом;
- после запуска контейнера работают `/health`, `/predict` и `/docs`;
- временные файлы, токены и локальные конфигурации не попадают в image.

Разрешённые базовые семейства images:

- официальный `python` с зафиксированной версией;
- официальный `ubuntu` с зафиксированной версией;
- `nvidia/cuda` с зафиксированными CUDA, runtime и Ubuntu;
- специализированный image, если его необходимость объяснена в `README.md` и
  согласована с преподавателем.

Использование непредсказуемого плавающего тега без версии не допускается.

Проверяемый результат:

- image собирается на чистой машине;
- сервис запускается одной документированной командой;
- после запуска автоматическая smoke-проверка получает успешный ответ
  `/health` и выполняет один корректный запрос `/predict`.

Баллы:

| Критерий | Баллы |
|---|---:|
| Воспроизводимая сборка image | 4 |
| Безопасная структура Dockerfile и `.dockerignore` | 3 |
| Запуск сервиса одной документированной командой | 3 |
| Работа `/health`, `/predict` и `/docs` в контейнере | 3 |
| Smoke-проверка собранного image | 2 |

### 3.3. Данные и эксперименты - 15 баллов

Используйте один или несколько инструментов, например ClearML, MLflow или DVC.
Инструмент выбирается по решаемой задаче, а не только по факту его наличия в
проекте.

Требования:

- проведено минимум три сравнимых эксперимента;
- для экспериментов сохранены параметры, метрики и используемая версия кода;
- показано минимум две версии датасета или воспроизводимого препроцессинга;
- для каждой версии данных известны источник, способ получения и идентификатор
  или контрольная сумма;
- описано единое правило разбиения на train, validation и test;
- test-выборка не используется для подбора гиперпараметров;
- выбран лучший эксперимент и объяснён критерий выбора;
- модель итогового эксперимента сохранена в доступном artifact или model
  registry;
- большие данные и модели не добавлены в обычную историю Git без согласования.

ClearML может использоваться для экспериментов и версий Dataset. DVC может
использоваться для данных и воспроизводимых стадий. MLflow закрывает учёт
экспериментов и моделей, но версия данных при этом должна фиксироваться
отдельным воспроизводимым способом.

Проверяемый результат:

- по идентификатору эксперимента можно определить код, данные, параметры и
  метрики;
- итоговую модель можно получить повторно или скачать из указанного хранилища;
- результаты трёх экспериментов сравниваются по одной и той же методике.

Баллы:

| Критерий | Баллы |
|---|---:|
| Три корректно зафиксированных эксперимента | 4 |
| Две воспроизводимые версии данных или препроцессинга | 4 |
| Корректное разбиение и единая методика оценки | 3 |
| Обоснованный выбор итоговой модели | 2 |
| Доступный artifact модели и связь с экспериментом | 2 |

### 3.4. Инференс-сервис и тесты - 15 баллов

Сервис реализуется на FastAPI или другом согласованном HTTP-фреймворке.

Обязательные endpoints:

- `GET /health` - сообщает о готовности приложения и модели;
- `POST /predict` - принимает входные данные и возвращает предсказание;
- `/docs` - содержит автоматически сформированную документацию API.

Требования к контракту:

- формат запроса и ответа описан схемами;
- приведён минимум один корректный пример запроса;
- неправильные данные возвращают понятный клиентский HTTP-код и сообщение;
- ответ содержит версию модели или другой однозначный идентификатор;
- preprocessing сервиса соответствует preprocessing итогового эксперимента;
- один запрос не изменяет состояние модели для следующего запроса;
- в репозитории есть автоматические тесты.

Минимальный набор тестов:

- успешный `/health`;
- успешный `/predict` на небольшом фиксированном примере;
- ошибка `/predict` на некорректном входе;
- проверка основной схемы ответа;
- тест преобразования входных данных без запуска внешней инфраструктуры.

Проверяемый результат:

- тесты запускаются одной документированной командой;
- сервис обрабатывает корректный запрос;
- неправильный запрос не приводит к необработанному исключению;
- версия модели в ответе соответствует итоговому artifact.

Баллы:

| Критерий | Баллы |
|---|---:|
| Контракт `/health`, `/predict` и `/docs` | 4 |
| Корректный preprocessing и использование итоговой модели | 4 |
| Автоматические позитивные и негативные тесты | 4 |
| Обработка ошибок и идентификатор версии модели | 3 |

### 3.5. Конфигурация и секреты - 10 баллов

Требования:

- настройки разделены минимум на секции `train` и `inference`;
- формат конфигурации явно выбран и описан;
- допускаются YAML, TOML, OmegaConf или другой обоснованный формат;
- переменные окружения используются для значений, зависящих от среды запуска;
- секреты отсутствуют в Git, Docker image, notebook outputs и логах;
- в репозитории есть безопасный шаблон конфигурации;
- обязательные значения проверяются при запуске;
- пути к данным и модели не привязаны к компьютеру автора;
- итоговые параметры обучения сохранены вместе с экспериментом.

Файл `.env` не является системой версионирования конфигурации. Реальный `.env`
не добавляется в Git. В репозитории хранится только пример без секретных
значений.

Проверяемый результат:

- проект запускается после заполнения документированного шаблона;
- отсутствие обязательного значения приводит к понятной ошибке;
- переключение между train и inference не требует изменения исходного кода.

Баллы:

| Критерий | Баллы |
|---|---:|
| Разделение train и inference | 3 |
| Переносимые пути и проверка обязательных параметров | 3 |
| Безопасная работа с секретами и шаблон настроек | 3 |
| Связь конфигурации с экспериментом | 1 |

### 3.6. Документация - 10 баллов

В репозитории должны находиться:

- `README.md`;
- `MODEL_CARD.md`;
- `DATASET_CARD.md`;
- схема архитектуры или ML-процесса.

`README.md` должен содержать:

- назначение проекта;
- требования к окружению;
- восстановление зависимостей;
- получение данных и модели;
- запуск тестов;
- обучение или воспроизведение итогового эксперимента;

`MODEL_CARD.md` должен содержать:

- назначение и ограничения модели;

- preprocessing;
- ограничения и известные проблемы данных;
- идентификаторы используемых версий.

Схема должна показывать путь данных от подготовки и обучения до model artifact
и HTTP-инференса. Если в проекте есть CI, его схема описывается отдельно.

| Понятная схема проекта | 2 |

### 3.7. Материалы для сдачи - 5 баллов

## 4. Дополнительные компоненты - не более 20 баллов

Можно выполнить несколько дополнительных компонентов, но в итоговую сумму
засчитываются два лучших результата. Каждый компонент оценивается максимум в
10 баллов.

### 4.1. Continuous Integration - до 10 баллов

Настройте GitLab CI, GitHub Actions или другую согласованную CI-систему.

Pipeline должен:

- проверять форматирование и качество кода;
- запускать тесты;
- требовать установленный порог покрытия;
- публиковать структурированный отчёт тестов и coverage artifact;
- собирать Docker image только после успешных проверок;
- выполнять smoke test `/health` для собранного image;
- запускаться для merge request и основной ветки;
- обрабатывать версионный Git tag;
- не создавать дублирующиеся pipeline для одного merge request;
- использовать commit SHA как один из идентификаторов image;
- не содержать секретов в конфигурации и логах.

Для проверки предоставляются ссылка на успешный pipeline и commit SHA. Успешная
YAML-валидация без запуска jobs не считается выполненным CI.

Баллы:

| Критерий | Баллы |
|---|---:|
| Lint, tests и порог coverage | 3 |
| Отчёты и воспроизводимое окружение jobs | 2 |
| Docker build после успешных проверок | 2 |
| Smoke test и очистка временного контейнера | 2 |
| Корректные правила branch, merge request и tag | 1 |

### 4.2. Continuous Delivery или Deployment - до 10 баллов

CD оценивается отдельно от CI. Наличие job с именем `deploy` само по себе не
подтверждает развёртывание.

Требования:

- развёртывается image, уже прошедший CI;
- среда развёртывания и адрес сервиса описаны;
- секреты хранятся вне репозитория;
- после развёртывания выполняется health check;
- версия запущенного сервиса определяется по image tag или digest;
- предусмотрен откат к предыдущей рабочей версии;
- production deployment требует ручного подтверждения или защищённого тега;
- неуспешная проверка не оставляет частично обновлённый сервис без объяснимого
  состояния.

Для проверки предоставляются ссылка на deployment job, адрес среды и
демонстрация отката.

### 4.3. Специализированный inference provider - до 10 баллов

Можно использовать один из вариантов:

- BentoML;
- Triton Inference Server;
- TGI или vLLM для языковой модели;
- другой согласованный inference runtime.

Требования:

- выбор инструмента соответствует типу модели;
- конфигурация runtime находится в репозитории;
- запуск воспроизводим;
- определены входы, выходы, типы и формы данных;
- есть health check и реальный запрос inference;
- FastAPI либо обращается к provider, либо его роль в архитектуре явно
  объяснена;
- документация не называет UI или control plane HTTP endpoint модели.

### 4.4. Оптимизация и упаковка модели - до 10 баллов

Допускаются:

- экспорт в ONNX;
- TensorRT;
- OpenVINO;
- квантизация;
- другой согласованный способ оптимизации.

Сам факт появления файла модели не является достаточным результатом.

Требования:

- экспорт выполняется воспроизводимым скриптом;
- проверяются входы, выходы, типы и формы;
- оптимизированная модель запускается на реальном примере;
- результат сравнивается с исходной моделью по заранее выбранному допуску или
  метрике;
- измеряются latency и размер artifact;
- сравнение выполняется на одинаковых данных и оборудовании;
- объясняется влияние оптимизации на точность и производительность.

### 4.5. Пользовательский интерфейс - до 10 баллов

Можно использовать Gradio, Streamlit, Hugging Face Spaces или другой
согласованный инструмент.

Требования:

- UI обращается к документированному inference API, а не содержит отдельную
  скрытую реализацию модели;
- пользователь может передать корректный вход и увидеть результат;
- ошибки сервиса отображаются понятно;
- показана версия модели;
- запуск интерфейса воспроизводим;
- в документации описана связь UI, API и модели.

## 5. Итоговая оценка

Обязательная часть даёт максимум 80 баллов. Из дополнительных компонентов
засчитывается максимум 20 баллов. Итоговая сумма ограничена 100 баллами.

| Итоговый балл | Оценка |
|---:|---|
| 0-60 | Неудовлетворительно |
| 61-70 | Удовлетворительно |
| 71-80 | Хорошо |
| 81-100 | Отлично |

Чтобы получить оценку выше 80, необходимо выполнить хотя бы один
дополнительный компонент. Для 100 баллов нужно получить все 80 обязательных
баллов и 20 дополнительных.

Проект не принимается до исправления критической проблемы, если:

- репозиторий или итоговый tag недоступен;
- в репозитории опубликован действующий секрет;
- зависимости невозможно восстановить по инструкции;
- Docker image не собирается;
- сервис не запускается;
- `/predict` не выполняет inference итоговой модели.

После исправления критической проблемы проект оценивается по обычной балльной
системе.

- итоговый tag указывает на нужный commit;

- демо и отчёт относятся к тому же commit SHA, который отмечен итоговым tag.
